# 需求挖掘报告 · 极境 ZenithLens

> 唯一输入：`docs/PROJECT_BRIEF.md`（OpenCode 独立重做版，status=confirmed）。
> 设计基准（只参照样式）：`docs/00-charter/00-design-reference-legacy-v2.html`。
> 本报告只写"要什么"，不写"怎么实现"；技术选型留给架构师。

## 摘要

1. 用户是**一个人、一台 Windows、22 只场外基金、每天看一次**，要的是"今天该不该动"的一句话判断，不是更多图表。
2. 三大核心问题：**方向判断**（涨/跌 + 可信度 + 组合覆盖）、**实时估值保真**（五档降级 + 来源徽章 + 估值≠净值）、**可审计**（任何判断可回溯、台账只增不改）。
3. 立身之本 = **可验证的预测**：跑不赢基线 `max(恒涨,恒跌)` 就自动灰显，绝不把"看起来能预测其实不能"的资产标为可信。
4. 本报告收敛出 **18 条需求**，其中 P0 = 12 条（最小闭环）、P1 = 5 条、P2 = 1 条。
5. 已剔除用户提的"解法型愿望"（如"加更多图表""接 LLM 做预测"），只保留露出真场景的条目。

## 正文

### 0. 需求挖掘方法说明（连问三层「为什么」）

以用户最常提的一句诉求演示：

```
用户说：我想看昨天的收益
→ 为什么？        想知道整体今天是赚了还是亏了
→ 为什么现在看不到？要手动打开 App 一只只点
→ 为什么要一只只点？持仓 22 只，没有汇总
→ 真需求：打开就能知道"整体今天是赚是亏、哪几只拖后腿"
```

**判定规则**：没有「场景」和「痛点」的条目一律算愿望，不进本报告。
下方每条需求均标注来源（Brief 章节号 = 用户书面诉求）。

---

### A 组 · 看懂持仓与估值（对应 Brief §3.2、§5.4）

#### R-01 · 打开即见组合总览
- **优先级**：P0
- **来源**：PROJECT_BRIEF §1「每天需要『今天该不该动』的判断依据」
- **场景**：用户持 22 只场外基金，每天收盘后打开产品，第一眼想知道"整体今天赚了还是亏了"。
- **痛点**：现在要一个个打开基金 App 点开每只基金，22 只点完才拼出全貌，无法一眼判断。
- **需求**：打开首页即同时看到 **总资产 / 今日预估盈亏 / 累计收益 / 收益率** 四个汇总数字。
- **验收**：首页首屏渲染完成后，一屏之内同时可见上述 4 个数字；总资产 = Σ(份额 × 最新估值)，与逐行明细求和误差为 0；4 个数字均可点开查看口径说明（分子/分母来源）。

#### R-02 · 实时估值五档降级保真
- **优先级**：P0
- **来源**：PROJECT_BRIEF §3.2「官方净值 / 盘中估算 / 重仓加权 / 代理近似 / 未知 五档降级链」
- **场景**：用户盘中/盘后想看某只基金今天的涨跌，但场外基金官方净值要到很晚才公布。
- **痛点**：官方净值没出时只能看估算，而估算值和真实净值长得一模一样，不标注就会把"猜的"当成"既成事实"。
- **需求**：每只基金今日涨跌按 **五档降级链** 取数：official（官方净值）→ intraday（盘中估算）→ holdings（重仓加权）→ proxy（代理近似）→ unknown（未知）；降级顺序由后端决定，前端只如实呈现。
- **验收**：任意持仓行的估值来源徽章必须等于后端返回的 `mode` 字段，不得静态硬编码；降级到 unknown 时该行不显示任何今日涨跌数值；同一基金同日只能处于一档。

#### R-03 · 估值 ≠ 净值，来源可区分可追溯
- **优先级**：P0
- **来源**：PROJECT_BRIEF §3.2「估值 ≠ 净值，两者来源必须可区分、可追溯」
- **场景**：用户想核对"这个数是官方公布的，还是系统算的"。
- **痛点**：估算与净值混在一个字段里，事后无法追溯当时用的是哪一档、经过什么降级路径。
- **需求**：估值（今日预估值）与净值（已公布官方值）是两个独立字段；每个估值行附**来源徽章 + 降级链路**，可展开查看。
- **验收**：数据模型中估值与净值字段名不同且互不覆盖；徽章悬浮/展开可见降级链路（如 official 未出 → 尝试 intraday → 命中）；对同日同一基金，官方净值回填后不得改写当日已入账的估值记录来源。

#### R-04 · 未知 ≠ 持平
- **优先级**：P0
- **来源**：PROJECT_BRIEF §5.4「未知 ≠ 持平」
- **场景**：某只基金今天没有任何可信估值来源。
- **痛点**：若渲染成 `+0.00%`，用户会读成"今天没涨没跌"，把"没有数据"说成"没有波动"。
- **需求**：无可信估值时，涨跌列渲染为「未知」、今日盈亏列渲染为「—」，且汇总处显式声明未覆盖只数。
- **验收**：当某行 pct 为空/未知，界面**绝不出现** `+0.00%`；汇总卡标注"仅覆盖 N/M 只，其余未知不计入"；全量未知时今日盈亏显示「未知」而非 0。

#### R-05 · 覆盖度分级说明（A/B/C/D）
- **优先级**：P0
- **来源**：PROJECT_BRIEF §4「把『看起来能预测其实不能』的资产标为可信 → 比不做更糟」；§8「宁可只覆盖少数资产但每个数字都 trustworthy」
- **场景**：用户想知道 22 只里哪些信号可信、哪些只是占位。
- **痛点**：不区分就把未验证资产和已验证资产一视同仁，等于把"猜的"混进结论。
- **需求**：每只基金标注覆盖档位 **A 已接入 / B 代理已验证 / C 代理待验证 / D 暴露待定**，并给出每档依据与只数/市值/占比。
- **验收**：首页可见四档分级面板，含每档只数、市值、占比；C/D 档在信号列显示「待验证」/「暴露待定」，不得显示为可信信号；分级依据可展开阅读。

#### R-06 · 隐私打码
- **优先级**：P1
- **来源**：PROJECT_BRIEF §5.4「隐私打码（隐藏金额）」
- **场景**：用户在有人在场时打开产品。
- **痛点**：金额直接暴露。
- **需求**：一键隐藏所有金额（总资产/盈亏/持仓金额），占比与涨跌幅保留。
- **验收**：打开开关后所有金额位渲染为 `••••`；占比与百分比涨跌仍可见；刷新后开关状态保持（本地记忆）。

### B 组 · 方向判断与预测（对应 Brief §3.1、§4、§5.1、§5.2）

#### R-07 · 单只基金方向预测信号
- **优先级**：P0
- **来源**：PROJECT_BRIEF §3.1「对能预测的资产给出未来 N 天涨/跌方向 + 可信度」；§5.1 预测核心逻辑
- **场景**：用户想知道某只已接入基金明天（T+1）是涨还是跌。
- **痛点**：没有可验证的方向判断，只能凭感觉。
- **需求**：按 **E1 跳空 / E3 无量急跌触发门 → DDSM 状态模型 → 双否决（拥挤度 + KLOW2）→ 出口 P > 0.52** 输出"涨"信号；不满足则"灰（不表态）"，**永不做空**。
- **验收**：每条信号必须同时给出触发门名称、P 值、否决层状态；`P ≤ 0.52` 一律不输出"涨"；任一否决亮灯输出"弃权"；界面无任何"做空/卖空"入口。

#### R-08 · 信号全链路可解释
- **优先级**：P0
- **来源**：PROJECT_BRIEF §3.3「任何一次判断可回溯（凭什么、用的什么数据）」
- **场景**：用户看到一个"涨"信号，想知道凭什么。
- **痛点**：黑盒信号无法建立信任。
- **需求**：每条信号可展开显示 **6 步链路**：①触发门 ②DDSM 档位 ③拥挤度否决 ④KLOW2 否决 ⑤出口判定 ⑥输出。
- **验收**：展开后 6 步齐全，且每步带具体数值（如 `ret −3.82%`、`量比 0.72`、`P=0.61`、`z 分位`、`下影线比`）；数值缺失的步骤显示"数据缺失"而非留空。

#### R-09 · 组合层三窗口加权预测
- **优先级**：P0
- **来源**：PROJECT_BRIEF §3.1「组合层给『组合加权 P + 覆盖市值占比』，覆盖不足必须显式声明」
- **场景**：用户想知道"整体今天能不能动"。
- **痛点**：单只信号没有组合视角，无法决策。
- **需求**：给出 **T+1 / T+3 / T+15** 三窗口组合加权 P，规则为：**只有开口仓位计入权重**（灰不是 0.5，是从分子分母同时剔除）、**C/D 档不参与**、**必须同时显示覆盖市值占比**。
- **验收**：每个窗口同时显示「组合加权 P」与「覆盖市值占比」两个数字，且标注覆盖金额；当覆盖市值 < 100% 时，界面显式写出"其余 X% 不表态"；三窗口缺基线数据时标注"待填充"。

#### R-10 · 预测成绩对照基线（报 Δ 而非裸命中率）
- **优先级**：P0
- **来源**：PROJECT_BRIEF §4「T+1 方向正确率不跑赢基线（基线 = max(恒涨, 恒跌)）→ 产品无价值」；§5.1「报增量 Δ，不报裸命中率」
- **场景**：用户想知道这套预测到底有没有价值。
- **痛点**：裸命中率可以被高基线掩盖（例如全市场恒涨 55%，模型 56% 其实没本事）。
- **需求**：任何成绩展示都必须与**同期基线 `max(恒涨, 恒跌)`** 并列，主指标为增量 **Δ**。
- **验收**：复盘页同时显示「命中率 / 基线 / 开口数 / Δ」四列；Δ 旁标注基线口径来源；无基线数据的窗口显示"待填充"，**不得用估计值填充**。

#### R-11 · 走前验证与冻结 holdout（方法论约束）
- **优先级**：P0
- **来源**：PROJECT_BRIEF §5.2「走前时序 CV（禁随机切分）· purge gap = H+2 · placebo ≥2pp · 冻结 holdout 60 日禁调参」
- **场景**：用户在审计这套系统本身是否诚实。
- **痛点**：随机切分/事后调参会制造虚高回测，无法区分真本事与过拟合。
- **需求**：所有回测成绩必须来自**走前时序 CV**，purge gap = H+2，冻结 holdout 60 日不参与调参，新结论须过 placebo ≥2pp。
- **验收**：复盘页成绩卡标注"走前 CV"字样与 purge gap 口径；holdout 窗口在调参期间冻结、界面不得出现 holdout 调参痕迹；任何新因子结论附 placebo 检验值。

#### R-12 · 审计台账 INSERT-ONLY + 到期回填
- **优先级**：P0
- **来源**：PROJECT_BRIEF §3.3「台账 INSERT-ONLY」；§5.2「台账 INSERT-ONLY」
- **场景**：用户事后想核对某天到底出了什么信号、结果如何。
- **痛点**：台账能被改 = 事后诸葛，无法证伪。
- **需求**：每次开口在**收盘时点固定写盘、只增不改**，到期自动回填 T+1/T+3/T+15 实际涨跌。
- **验收**：台账每条记录含 `date / code / gate / p_up / ddsm_state / veto_crowd / veto_klow2 / signal / t1_real / t3_real / t15_real`；界面无"编辑/删除台账"入口；同一天同一 code 不可重复写入；回填只写 `t*_real` 字段，不动 `signal`。

#### R-13 · 三窗口口径定义与可执行路径说明
- **优先级**：P1
- **来源**：PROJECT_BRIEF §3.1「未来 N 天」；§5.3「QDII 的 T+2 是信息优势不是缺陷」；设计基准分析页口径
- **场景**：用户看到"明日涨 58%"会误以为当天就能买入。
- **痛点**：场外基金 15:00 截止申购、信号 15:30 才出，口径不说清会误导操作。
- **需求**：明确定义 T+1 为 `close[T+1] > close[T]`，并说明三种执行路径（A 新建仓位 / B 已持有仓位 / C 场内 ETF）中哪条可执行。
- **验收**：口径定义可展开阅读；明确写出"对场外基金最现实的用法是 B（持有/赎回决策）"；不得出现暗示"当天可买入"的文案。

### C 组 · 治理、操作与工程底线

#### R-14 · 因子治理可视化
- **优先级**：P1
- **来源**：PROJECT_BRIEF §8「再做覆盖度 B/C/D 档扩展与因子治理」
- **场景**：用户想审计因子是否在健康地进化/淘汰。
- **痛点**：因子增删无留痕，无法判断"哪个因子真的有用"。
- **需求**：展示四盘（正式/淘汰影子/有效因子影子/冷冻）、四本账本、评分链与生命周期规则。
- **验收**：四个盘面各自可见因子列表与角色；至少可见 4 本账本的用途与最近记录；评分链的悬崖规则与窗口权重可见。

#### R-15 · 引擎观测台
- **优先级**：P1
- **来源**：PROJECT_BRIEF §1「审计这套系统本身是否诚实」；设计基准引擎页
- **场景**：用户想知道引擎此刻在不在线、台账写到哪了。
- **痛点**：引擎黑盒，出问题无从察觉。
- **需求**：只读展示引擎状态 HUD、影子盘台账状态与最近记录、DDSM 状态表、冻结参数、六维输入快照。
- **验收**：HUD 展示运行状态与最近更新时间；台账记录显示字段清单；DDSM 冻结参数（K=4 / p=0.25 / MIN_N=15 / SHRINK=10 / BAND=0.02）可见且标注"改动须重走六关"；本页只读无编辑入口。

#### R-16 · 数据源健康可见
- **优先级**：P1
- **来源**：PROJECT_BRIEF §5.3「行情主通道：腾讯…实时估值走腾讯/天天基金/新浪」（接口随时可能被墙）
- **场景**：某天估值异常，用户要判断是数据源挂了还是引擎坏了。
- **痛点**：数据源不可见，故障无法定位。
- **需求**：设置页展示各数据源连通状态、最近成功时间、失败次数。
- **验收**：每个数据源显示 正常/不通/波动 三态之一 + 最近时间戳；不通常见时首页出现降级提示条。

#### R-17 · 持仓录入与加减仓
- **优先级**：P1
- **来源**：PROJECT_BRIEF §2「持 22 只场外基金」；§5.3 持仓读 `app_data/funds_data.json`
- **场景**：买入/卖出后需要更新持仓。
- **痛点**：持仓数据与产品脱节。
- **需求**：支持录入/编辑基金（代码、名称、金额或份额、成本、确认天数 T+1/T+2/T+3）、加仓/减仓、删除（二次确认）。
- **验收**：基金代码校验为 6 位数字；金额与份额至少填一项；删除需二次确认；改动后总览与明细同步刷新，数值与持仓数据一致。

#### R-18 · 启动可靠性（Python 3.8+ / 桌面 exe）
- **优先级**：P0
- **来源**：PROJECT_BRIEF §4「Python 3.8+ 跑不起来 / exe 点『启动』无反应 → 交付失败」；§5.3「必须能在 Python 3.8+ 直接 `python app.py` 起服」
- **场景**：用户双击启动产品或执行起服命令。
- **痛点**：以前版本出现过启动无反应、版本不兼容。
- **需求**：交付物无需第三方依赖即可在 Python 3.8+ 起服；桌面 exe 点击"启动"须有明确反馈。
- **验收**：在 Python 3.8 环境下执行 `python app.py` 可成功起服并访问 `http://127.0.0.1:<port>`；exe 点击"启动"后 ≤10s 内出现窗口或明确的错误提示（不得静默无反应）；启动失败须在界面/日志给出可读原因。

#### R-19 · 本地离线与数据不出本机
- **优先级**：P0
- **来源**：PROJECT_BRIEF §2「本地部署不联网」；§7「本地单用户 web + 桌面 exe，不联网部署」
- **场景**：用户在意隐私与离线可用。
- **痛点**：联网产品有数据外泄与断网不可用风险。
- **需求**：本地单用户部署，数据只存本机；除行情/估值取数外不发生外部上传。
- **验收**：设置"关于"明确声明本地存储、数据不出本机、不构成投资建议；无多用户/登录/云同步入口；断网时已缓存数据仍可查看。

#### R-20 · LLM 编码器（shadow 观察区，非预测）
- **优先级**：P2
- **来源**：PROJECT_BRIEF §5.5「事件维接入 DDSM（三窗口无增量）」；设计基准设置页 LLM 接口
- **场景**：用户预留事件编码能力，但明确它不做最终预测。
- **痛点**：把未验证的事件维当生产结论会污染预测。
- **需求**：LLM 仅用于**事件编码**，输出必须先过四关回测才能进生产；当前停在 shadow/观察区，界面明确标注。
- **验收**：界面标注"仅用于事件编码，不做最终预测 / 当前 shadow 观察区"；温度、输出格式等硬约束可见；事件维未过回测前不得出现在信号链中。
